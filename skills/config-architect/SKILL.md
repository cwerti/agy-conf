# Config Architect & Consultant Workflow

Use this skill whenever the user wants to brainstorm, discuss, or plan changes to their agent configuration repository (`agy-conf`), for example:
- *"Помоги настроить конфиг"*
- *"Хочу добавить что-то для работы с Celery / Docker / RabbitMQ"*
- *"Давай обсудим, как лучше настроить правила для нового проекта"*
- *"Что ещё можно улучшить в моём окружении?"*

---

## 🏛️ Полный контекст репозитория `agy-conf`

Как архитектурный консультант, вы должны в совершенстве знать структуру и ограничения текущего окружения:

### 1. Профиль разработчика и окружения
- **ОС**: Windows (PowerShell / `pwsh`). Все команды должны быть совместимы с Windows, пути — через `pathlib.Path` или `/`, кодировка файлов — строго `encoding="utf-8"`.
- **Стек**: Python, FastAPI, SQLAlchemy 2.0 (async), Alembic, Pydantic v2, PostgreSQL, Redis.
- **Пакетный менеджер**: Стандартные `venv`, `poetry`, `pip`. **Строго без `uv`**.
- **Два рабочих контура**:
  - **Рабочий**: Корпоративный self-hosted GitLab + JetBrains YouTrack. Любой `git push` требует подтверждения пользователя.
  - **Личный**: GitHub (`AGENT_MEMORY_REPO_URL`). `git push` разрешён автоматически для синхронизации логов и памяти.

### 2. Матрица выбора типа кастомизации
Когда пользователь предлагает идею, помогите ему выбрать правильный инструмент:

| Потребность | Рекомендуемый тип | Куда поместить | Примеры |
| :--- | :--- | :--- | :--- |
| **Постоянный принцип или ограничение** | **Правило (Rule)** | `rules/<имя>.md` + ссылка в `AGENTS.md` | Правила написания тестов, запрет блокирующего I/O, стиль Pydantic v2 моделей. |
| **Пошаговый сценарий или инструкция** | **Навык (Skill)** | `skills/<имя>/SKILL.md` | Сценарий выпуска релиза, генерация миграции Alembic, диагностика контейнеров. |
| **Доступ к внешним данным или сервисам** | **MCP Сервер** | `mcp/mcp_config.json` | Просмотр схемы PostgreSQL, очередей Redis, чтение issues в YouTrack. |
| **Разрешение или запрет команд шелла** | **Политика безопасности** | `security/commands.json` | Разрешить `pytest` без вопросов, запретить `alembic downgrade base`. |
| **Архитектурное решение или опыт** | **Долгосрочная память** | `memory/context.md` / `memory/sessions/` | Зафиксировать выбор конкретной библиотеки или схему авторизации. |

## 💬 Протокол консультации (Шаг за шагом)

### Шаг 1: Интервью и выявление потребностей
1. Внимательно выслушайте идею пользователя.
2. Задайте 1–2 уточняющих вопроса, если задача размыта (например: *"Вы хотите, чтобы агент всегда следовал этому правилу при написании кода, или это должна быть команда, которую вы вызываете по требованию?"*).
3. Проанализируйте влияние на контекст (Rule загружается часто, а Skill — только по требованию, экономя токены).

### Шаг 2: Предложение архитектурного решения
Сформулируйте предложение по пунктам:
* **Что создаём**: (например, правило `rules/celery.md` + команда в `security/commands.json`).
* **Почему именно так**: обоснование с точки зрения расхода токенов и удобства.
* **Черновик контента**: покажите пользователю краткий проект изменений (структуру файла, правила, команды).
* **Согласование**: спросите пользователя: *"Вносим эти изменения или скорректируем детали?"*.

### Шаг 3: Реализация изменений (по согласию)
После подтверждения пользователем:
1. Создайте или обновите необходимые файлы (`rules/`, `skills/`, `mcp/`, `security/`).
2. Если добавлено правило — обновите [`AGENTS.md`](file:///D:/uriit/agy-conf/AGENTS.md) и [`GEMINI.md`](file:///D:/uriit/agy-conf/GEMINI.md).
3. Если добавлен MCP — обновите [`mcp/servers.md`](file:///D:/uriit/agy-conf/mcp/servers.md) и проверьте JSON через `python -m json.tool`.
4. Если изменена политика команд — протестируйте её через:
   ```powershell
   python security/check_command.py "<тестовая_команда>"
   ```
5. Проверьте `git status`. **Никаких пушей не делать** без отдельного указания пользователя.

### Шаг 4: Итоговый отчет
Кратко покажите, какие файлы созданы/изменены, и как теперь использовать новую возможность.
